# Mobile Offline Architecture
**Denver Engineering — Ava Phase 3 (v4.35.0)**

## Purpose

Field workers operate in environments with unreliable connectivity (basements, plant floors, remote sites). The mobile offline architecture allows them to capture and submit work without connectivity, then sync reliably when connection is restored — without duplicating or losing data.

## Core Principles

- **Idempotency:** Every mutation carries a `client_id` (UUID generated by the device). Re-submitting the same mutation is safe — the server detects the duplicate and skips re-application.
- **Conflict detection:** When server state has changed since the device's last sync, a conflict is recorded rather than silently overwriting either version.
- **Explainable resolution:** All conflict strategies are logged with their rationale.
- **Audit continuity:** Offline mutations retain the original `submitted_by` and `submitted_at` timestamps from the device.

## Data Flow

```
Field Device
  │ [offline: queue mutations locally]
  │ [online: POST /api/v1/sync/upload]
  │
  ▼
syncEngine.processSyncUpload()
  │
  ├── Register device (upsert mobile_devices)
  ├── Create sync_session (track stats)
  │
  └── For each OfflineMutation:
        │
        ├── Check idempotency: SELECT from offline_mutations WHERE client_id = ?
        │   └── If found → skip (already applied), count as duplicate
        │
        ├── Dispatch to entity handler:
        │   ├── _applyPunchMutation (punch_items)
        │   ├── _applyInspectionMutation (inspections)
        │   ├── _applyDailyLogMutation (daily_log_entries)
        │   └── _applyGenericMutation (all other entities)
        │
        ├── On success → record in offline_mutations (applied)
        └── On ConflictError → record conflict in offline_conflicts,
                               record mutation (conflict)

  ▼
SyncResult {
  session_id, applied, skipped, conflicts,
  conflict_ids[], server_watermark
}
```

## Idempotency Mechanism

```sql
-- offline_mutations constraint
UNIQUE(tenant_id, device_id, client_id)
```

Before applying any mutation, `applyMutation()` checks:

```sql
SELECT id FROM offline_mutations
WHERE tenant_id = $1 AND device_id = $2 AND client_id = $3
```

If found, the mutation is counted as `skipped` and returned with `status: 'duplicate'`. The device can safely re-upload its entire pending queue without risk.

## Conflict Detection

A conflict occurs when the server entity has been modified more recently than the device's recorded `last_synced_at`. The engine raises a `ConflictError`:

```typescript
class ConflictError extends Error {
  constructor(
    public entityId: string,
    public serverVersion: Record<string, unknown>,
    public conflictType: 'update_update' | 'update_delete' | 'schema_mismatch'
  ) { super('conflict') }
}
```

The conflict is persisted to `offline_conflicts` with both `client_version` and `server_version` for later resolution.

## Conflict Resolution Strategies

| Strategy | Behavior | Fields |
|----------|----------|--------|
| `client_wins` | Client payload overwrites server | All fields |
| `server_wins` | Server version retained, client discarded | All fields |
| `merged` | Field-level merge (see below) | Mixed |
| `rejected` | Conflict marked resolved with no changes | None |

### Merge Rules (field-level)

| Field | Winner |
|-------|--------|
| `title`, `notes`, `description`, `attachments` | Client (content edits) |
| `status`, `priority`, `assignee_id`, `due_at` | Server (workflow state) |
| All other fields | Server |

### Auto-Strategy Selection

```typescript
function selectAutoStrategy(conflictType: string): ResolutionStrategy {
  if (conflictType === 'update_delete') return 'server_wins'
  if (conflictType === 'schema_mismatch') return 'rejected'
  return 'merged'  // update_update → attempt field-level merge
}
```

## Delta Pull

After uploading, devices pull events they missed while offline:

```
GET /api/v1/sync/pull?since=<watermark>&limit=200
```

Returns events from `realtime_event_log` since the watermark. The `server_watermark` in the response is the `published_at` of the latest event returned, which the device stores for the next pull.

## Schema

```sql
-- Device registry
CREATE TABLE mobile_devices (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid NOT NULL,
  device_token  text NOT NULL,
  push_token    text,
  platform      text NOT NULL CHECK (platform IN ('ios','android','web')),
  last_seen_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE(device_token)
);

-- Per-upload session tracking
CREATE TABLE sync_sessions (
  id                   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id            uuid NOT NULL,
  device_id            uuid NOT NULL REFERENCES mobile_devices(id),
  mutations_uploaded   int NOT NULL DEFAULT 0,
  mutations_applied    int NOT NULL DEFAULT 0,
  mutations_skipped    int NOT NULL DEFAULT 0,
  conflicts_detected   int NOT NULL DEFAULT 0,
  client_watermark     timestamptz,
  server_watermark     timestamptz,
  started_at           timestamptz NOT NULL DEFAULT now(),
  completed_at         timestamptz
);

-- Immutable mutation log (idempotency enforced by UNIQUE)
CREATE TABLE offline_mutations (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     uuid NOT NULL,
  device_id     uuid NOT NULL REFERENCES mobile_devices(id),
  client_id     text NOT NULL,           -- device-generated UUID
  entity_type   text NOT NULL,
  entity_id     uuid,
  operation     text NOT NULL,
  payload       jsonb NOT NULL DEFAULT '{}',
  status        text NOT NULL DEFAULT 'applied',
  conflict_id   uuid REFERENCES offline_conflicts(id),
  submitted_by  uuid NOT NULL,
  submitted_at  timestamptz NOT NULL,
  received_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE(tenant_id, device_id, client_id)
);

-- Conflict records
CREATE TABLE offline_conflicts (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id       uuid NOT NULL,
  mutation_id     uuid REFERENCES offline_mutations(id),
  entity_type     text NOT NULL,
  entity_id       uuid,
  conflict_type   text NOT NULL,
  client_version  jsonb NOT NULL,
  server_version  jsonb NOT NULL,
  resolution      text,
  merge_result    jsonb,
  resolved_by     uuid,
  resolved_at     timestamptz,
  detected_at     timestamptz NOT NULL DEFAULT now()
);
```

## API Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/sync/upload` | Submit offline mutation batch |
| `GET` | `/sync/pull` | Pull delta events since watermark |
| `POST` | `/sync/devices/register` | Register device token |
| `GET` | `/sync/conflicts` | List unresolved conflicts for tenant |
| `POST` | `/sync/conflicts/:id/resolve` | Resolve specific conflict |

## Known Limitations

- Maximum 500 mutations per upload batch (enforced in route handler).
- Merge strategy only handles flat payload keys; nested object merging reverts to server-wins.
- Delta pull is limited to 500 events per request; clients with large offline gaps must paginate via multiple pulls.
- Push notification tokens are registered but push delivery is not yet implemented (Phase 4).
