# Denver v2.0.1 — Post-Release Stabilization

**Type:** Operational stabilization (no features, no architecture/contract/governance changes).
**Goal:** eliminate pre-existing operational debt surfaced during the v2.0.0 release, on the production
runtime (Node 20).

## Fixes
- **Node 20 compatibility — evidence hashing.** `computeEvidenceHash` now digests a `Uint8Array` view of
  the file buffer, so it works across realms (jsdom Blob ↔ Node 20 webcrypto). Browser prod behavior
  unchanged; identical bytes → identical hash. (Fixes 4 `phase3-coverage` tests that failed only on
  Node 20.)
- **Node 20 compatibility — currency formatting.** Six compact-currency adapters add
  `trailingZeroDisplay: 'stripIfInteger'` so output is identical across ICU versions (`$420M` on Node 20
  and 24; `$1.5M` precision preserved). (Fixes `denver-engineering-next/backend-adapters` tests.)
- **CI determinism — timezone.** Test runs are pinned to `TZ=UTC` (vitest config), removing date-drift
  false failures between a developer's local zone and CI/prod (UTC).
- **Deployment pipeline — Render.** The deploy workflow now treats HTTP `409` (a deploy already in
  progress; Render's native auto-deploy fired for the commit) as success instead of failing. Restores a
  green deploy pipeline.

## Verification
- Full test suite on **Node 20.20.2: 5246/5246 pass** (even with shell `TZ=America/New_York` — config
  forces UTC).
- `tsc` (api+src and modules): 0 errors. Lint: within threshold.
- Runtime smoke on Node 20: clean DB migration (070–081), app boot, `/api/v1/health` 200 (db ok),
  `/metrics` 200, authz 401, no federation init errors.

## Not changed (out of scope)
- No federation contracts, APIs, schema, architecture, or governance changes.
- `denver-engineering-next/frontend/src/__tests__/render.test.tsx` remains excluded from the root runner
  (orphaned `@ds` alias from the app flatten); wiring the Next app's own test config is future work.
- Render deploy-hook **secret/service health** must still be confirmed on the Render dashboard (the 409
  implies a deploy was triggered, but live success is verified there, not from CI).
