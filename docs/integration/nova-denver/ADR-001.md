# ADR-001 — Nova ↔ Denver EPC Project Integration Architecture

Status: **Accepted** (user-approved 2026-07-20; independent security review verdict: APPROVE-WITH-CHANGES — amendments below are binding) · Date: 2026-07-20

## 0. Security-review amendments (binding, 2026-07-20)

1. **Atomicity**: on each receiver, ledger insert + state change + link write + outbox row happen in ONE database transaction; the command ledger stores the full response snapshot and replays return it.
2. **Connection-scoped verification**: parse body → load connection row by `connectionId` → verify HMAC against that connection's secret (per-connection resolver; shared env secret in v1) → require `status='connected'` → tenant derived only from the connection row. Never trust payload tenant IDs. A second connection requires a distinct secret. (The legacy `/api/cx/webhook` pattern of trusting payload `tenant_id` is explicitly NOT to be copied.)
3. **Idempotency conflicts**: ledger stores a raw-body SHA-256 digest; same key + different digest → 409 `idempotency_conflict`, never the stored response.
4. **Reconcile is a signed POST** (connectionId inside the signed body), not a GET with path params.
5. **No commercial values cross the boundary**: `commercialSummary` removed from the v1 contract; Denver never stores or logs contract values.
6. **Turnover links are plain deep links** (relative paths) requiring Denver login — no capability tokens in v1.
7. **URL fields are relative paths** matching `^/[A-Za-z0-9/_-]+$`; absolute URLs are dropped; UIs compose links from `*_PUBLIC_URL`.
8. **Dual-secret rotation**: receivers verify against `*_SECRET` and optional `*_SECRET_PREVIOUS`.
9. **Progress events via snapshot-diff worker job** (every 5 min, hash-compared per linked project, enqueued in the same transaction as the hash update) — not scattered mutation hooks.
10. **Stale guard on `(occurredAt, sequence)`** where `sequence` is the sender's monotonic outbox id.
11. Both raw-body receivers get dedicated rate limits + 1 MB body caps.
12. Nova production enablement (`DENVER_ENABLED`) is preconditioned on a CI workflow running the new integration tests (Nova currently runs no tests in CI).
13. Denver `nova_outbox`/`nova_connections` RLS treatment documented in the migration (worker drains cross-tenant via the privileged pool).
Inputs: `DISCOVERY_DENVER.md`, `DISCOVERY_NOVA.md`, HOB "Nova ↔ Denver EPC Project Integration"

## 1. Context

Nova (business operations: CRM, opportunities, projects, finance) must originate commercial projects and trigger creation of linked EPC projects in Denver (EPC execution: engineering, construction, commissioning, turnover). Denver must publish summarized progress and turnover status back to Nova. Neither app may become authoritative for the other's data; no monolith merge.

Discovery established a sharply asymmetric starting point:

| Capability | Denver | Nova |
|---|---|---|
| Multi-tenancy | Strong (app-layer + Postgres RLS, dual pools) | Strong (app-layer, server-side scoping) |
| Service-to-service auth | HMAC raw-body webhook receiver exists (`/api/cx/webhook`, Menlo pattern) | None (api_keys minted but never verified) |
| Durable jobs / retry | `background_jobs` + worker; connector framework with DB retry, dead-letter, idempotency | None (GitHub Actions cron only) |
| Outbound signed webhooks | Yes (HMAC-SHA256, delivery history) — retry not durable | None (design doc only) |
| Inbound idempotency ledger | Yes (`cx_inbound_events`, UNIQUE(tenant_id,event_id)) | None |
| Event vocabulary | `universalEvents.ts` (flag-gated) | None |
| Audit | `audit_log` (RLS, hash-chain verify) incl. `integrate_push/pull` actions | `tenant_audit_events` (append-only, broad coverage) |
| Migrations | Sequential SQL migrations (83) | Single idempotent `schema.sql` |
| Opportunity→project conversion | n/a | Fully built, audited, convert-once guarded |

## 2. Decision summary

**Mirror Denver's proven Menlo integration boundary in both directions, with Nova gaining its first machine-credential path.** Smallest reliable mechanism; no new infrastructure (no Kafka/RabbitMQ/broker), per HOB.

1. **Commands (Nova → Denver): HMAC-signed, versioned command endpoint on Denver**, outside the cookie/CSRF chain, modeled on `/api/cx/webhook`:
   - `POST /api/nova/commands` (raw-body HMAC-SHA256, `X-Nova-Signature: sha256=<hex>` over `${timestamp}.${body}`, `X-Nova-Timestamp` with ±5 min skew window, `timingSafeEqual`, 503 fail-closed if secret unconfigured).
   - First command: `project.create` (schemaVersion 1.0, per HOB contract). Validated manually per Denver convention (no zod), unknown `schemaVersion` → 422 rejection.
   - **Idempotency:** `nova_inbound_commands` table, `UNIQUE(tenant_id, idempotency_key)`; replay returns the original response (HOB: "Nova times out after Denver created the project; Nova retries" → same project, `status:"already_exists"`).
   - Response returns `denverOrganizationId (tenant id), denverProjectId, denverProjectNumber, projectUrl, createdAt` per HOB schema.

2. **Events (Denver → Nova): transactional-outbox rows in Denver, drained by the existing worker, delivered as HMAC-signed webhooks to a new Nova ingestion endpoint.**
   - Denver: new `nova_outbox` table (tenant_id, event_id UUID, event_type, payload JSONB, status queued/delivered/failed/dead, attempts, next_attempt_at, last_error, correlation_id). Written **in the same transaction** as the state change where practical; drained by a scheduler job handler in `api/worker.ts` (registered like the existing ~15 handlers) with bounded exponential backoff (reuse connector-framework backoff ladder `[30s,60s,5m,15m,1h]`) and dead-letter after max attempts. This deliberately does NOT reuse `dispatchWebhookEvent`'s in-process `setTimeout` retry (lost on restart — discovery §8).
   - Event types v1: `denver.project.created`, `denver.project.progress.updated`, `denver.turnover.package.updated`, `denver.integration.test` (connectivity check).
   - Progress payload assembled by a new read-only aggregator (`novaProgressProjection`) over `projects.progress_pct`, `current_phase`, turnover `computeCompleteness()`, `cx_status_mirror` counts, open deficiencies/punch/NCR, overdue actions — all existing rollups (discovery §14). Fields Denver cannot yet compute honestly (e.g. discipline-split engineering/procurement % if EVM/KPI snapshots absent for the project) are **omitted, not zero-filled** — Nova renders "not reported" (HOB honesty rule).
   - Nova: `POST /api/integrations/denver/events` mounted **before** JSON body parsing (raw body), HMAC verification per Nova's own documented scheme (`docs/CONVERSATION_HUB_WEBHOOK_SIGNING.md`: `X-Denver-Delivery` id, `X-Denver-Timestamp`, `X-Denver-Signature: v1=<hex>`), dedicated rate limit (customer-portal middleware pattern).
   - Nova idempotency + ordering: `denver_inbound_events` (`UNIQUE(tenant_id, event_id)`); projection update guarded by `occurredAt` — an older event never overwrites a newer projection (stale-event protection), but is still recorded.

3. **Mapping & connection model (both sides), tenant-safe by construction:**
   - **Nova:** `denver_connections` (tenant_id, connection_id, denver_org_id, status, secret refs are env-only in v1) and `denver_project_links` (tenant_id, project_id UNIQUE, connection_id, denver_project_id, denver_project_number, denver_project_url, integration_status, last_synced_at, last_error) + `denver_project_summaries` (Denver-derived projection, one row per link: overall stage, percents, counts, turnover status, as-of timestamp) + `denver_turnover_packages` (summary rows + secure link + superseded flag).
   - **Denver:** `nova_connections` (tenant_id, connection_id, nova_tenant_id, status) and `nova_project_links` (tenant_id, project_id UNIQUE, connection_id, nova_project_id, nova_project_number, nova_customer_name, contract_number, nova_project_url).
   - Every inbound message resolves tenant **from the connection record matched by connection_id + verified signature**, never from payload IDs alone. Mismatched `novaTenantId`/`connectionId` pairs are rejected and audited (`integration.rejected`).
   - v1 provisioning: one connection pair configured via env on both sides + a bootstrap script that inserts the connection rows (documented; this is a legitimate bootstrap-only insert). Multi-connection self-service UI is a later slice.

4. **Auth/SSO: secure deep links + independent authorization (interim account linking deferred).**
   - No shared IdP exists (Denver: cookie JWT + SAML/SCIM enterprise layer; Nova: cookie JWT only). Building OIDC now violates "smallest reliable mechanism."
   - v1: "Open in Denver" navigates to `DENVER_PUBLIC_URL + projectUrl`; Denver enforces its own login + tenant + role checks (deep link can never bypass — it's just a URL). Same in reverse for "Open in Nova". Documented explicitly as interim; OIDC/account-linking is the recommended next auth slice.

5. **Contracts:** versioned JSON Schemas checked into **both** repos under `docs/integration/nova-denver/contracts/v1/` (create-project request/response, progress event, turnover event, error envelope). Contract tests in each repo validate fixtures against the schemas — drift fails tests in both. No shared npm package in v1 (two repos, no shared registry — copies + checksum test is the smallest honest mechanism).

6. **Reconciliation:** 
   - Denver adds `GET /api/nova/reconcile/:connectionId` (HMAC-authed) returning current link map + latest summary versions.
   - Nova adds an admin-triggered reconcile action (and a script runnable by the existing GitHub-cron pattern) that compares its links/summaries against Denver's answer and classifies per HOB: healthy / nova_behind / delivery_pending / mapping_mismatch / auth_problem / remote_unavailable / manual_repair. Ambiguous mappings are flagged, never auto-repaired.

7. **RBAC:**
   - Nova: creating/retrying/repairing/disconnecting the Denver link = `requireTenantRole("admin","operations_manager")` (conversion itself stays as-is; the *integration* action is privileged). Read of the integration panel: any authenticated tenant member. Finance-only concept doesn't exist in Nova's role set; `member` cannot mutate integration state.
   - Denver: inbound commands act as the service principal (recorded actor = `nova-integration@<connection>`); Denver-side manual actions (retry, disconnect) gated `owner/admin` per existing inline-check convention.
   - RBAC tests both sides (403 paths, tenant-cross rejection).

8. **Audit:** every integration action/failure lands in the native audit stores — Denver `audit_log` (actions `integrate_push`/`integrate_pull` already in the enum) and Nova `tenant_audit_events` (`denver.connection.created`, `denver.project.create.requested/succeeded/duplicate/failed`, `denver.event.received/rejected/stale`, `denver.reconcile.run`, `denver.retry.manual`, …) with correlation IDs, no secrets/raw tokens in metadata.

9. **UI:**
   - **Nova** (`Project360Page.tsx` wiring layer, per locked-Stitch precedent): "Denver EPC Integration" panel — integration status chip, Denver project number, stage, discipline percents (with as-of timestamp), open critical deficiencies, overdue activities, systems ready/accepted, turnover status, last sync, Open in Denver, integration history (audit drill-down), Retry/Reconnect for authorized roles; "Create Denver EPC Project" action (review form pre-filled from project/customer/opportunity per HOB field list) shown when no link exists. Failure states render honestly (sync_failed ≠ green). Desktop density per Nova conventions.
   - **Denver** (project workspace + capability-registry entry, required by the feature-truth CI gate): "Nova Integration" panel — linked Nova tenant/project/number, customer, contract number, commercial PM, integration health, last outbound event, pending/failed deliveries (from `nova_outbox`), Open in Nova, audit history. Contract value is **not** displayed (HOB: role/product policy — v1 policy: hidden; Denver stores it only if sent, and v1 sends `commercialSummary` but Denver persists only in `nova_project_links` metadata, hidden from UI).

10. **Env & flags (both sides fail closed, per repo conventions):**
    - Denver: `NOVA_EXTERNAL` (master flag, default off), `NOVA_BASE_URL`, `NOVA_WEBHOOK_SECRET` (Denver→Nova signing), `NOVA_COMMAND_SECRET` (Nova→Denver verification), `NOVA_PUBLIC_URL`, `NOVA_TIMEOUT_MS` — mirrors `COMMISSIONING_*` naming exactly.
    - Nova: `DENVER_ENABLED`, `DENVER_BASE_URL`, `DENVER_COMMAND_SECRET` (signing), `DENVER_WEBHOOK_SECRET` (verification), `DENVER_PUBLIC_URL`. Added to `.env.example`. Missing secrets in production → integration endpoints return 503 / actions disabled with honest UI state (`authorization_required`), never a default secret.
    - Separate dev/staging/prod credentials; rotation = update env + restart (documented).

## 3. Options considered

**A. Service auth for Nova→Denver command**
- **A1. HMAC-signed raw-body endpoint (Menlo pattern) — CHOSEN.** Proven in-repo (webhook receiver + `cx_inbound_events`), symmetric with the reverse direction, no new token infrastructure, works with Denver's "tenant only from trusted context" rule via the connection registry.
- A2. Nova-issued JWT trusted by Denver — rejected: Denver verifies only its own `JWT_SECRET` (no issuer/audience support today); cross-trusting secrets couples the auth systems the HOB says not to rewrite.
- A3. API key on `/api/v1/projects` — rejected: would require adding a service-principal path through `requireAuth`/`requireTenant` (which deliberately removed header-tenant resolution); larger blast radius on the security-hardened main surface.

**B. Denver→Nova delivery**
- **B1. Dedicated `nova_outbox` + worker drain — CHOSEN.** True durable outbox (HOB explicitly asks for it); reuses existing scheduler/worker; avoids the known non-durable `setTimeout` retry in `dispatchWebhookEvent`.
- B2. Reuse migration-004 `webhooks` + `emitEvent` — rejected: retry not durable across restart; generic fan-out semantics complicate per-connection status ("pending deliveries for THIS Nova connection").
- B3. Ride the Integration Hub `integration_jobs` — considered; it has the right reliability semantics but is oriented to pull-style connector syncs with connector-health machinery not needed here. A thin dedicated outbox is smaller. (Revisit if a third partner appears.)
- B4. Nova polls Denver — rejected: Nova has no scheduler beyond GitHub cron (minutes-to-daily latency), and HOB requires event delivery with retry/failure visibility.

**C. Nova inbound ingestion**
- **C1. Raw-body HMAC endpoint + `denver_inbound_events` ledger — CHOSEN** (matches Nova's own webhook design doc and Denver's receiver pattern).
- C2. Verify via the dormant `api_keys` bcrypt path — rejected for v1: bcrypt-per-request cost, no request signing/replay protection, and the table's scopes/rate-limit semantics are unproven; HMAC gives integrity + replay windows for free.

**D. SSO**
- **D1. Independent auth + deep links — CHOSEN** for v1 (HOB sanctions "secure account linking as an interim solution"; we take the even smaller safe step and document it).
- D2. Shared OIDC IdP — correct end-state, out of scope for the first slice (new infra, both auth systems touched).

## 4. Source-of-truth matrix (enforced)

Per HOB §Source-of-Truth: Nova authoritative for customer/opportunity/contract value/commercial status/invoices/integration reference; Denver authoritative for all EPC/commissioning/turnover detail; the Nova-displayed commissioning summary is a **Denver-derived projection** stored in `denver_project_summaries` with `as_of` timestamp, read-only in Nova. Enforcement: Nova has no write path to Denver-owned fields (commands are create/reconnect only); Denver events can only touch the projection tables + integration status in Nova, never `projects` commercial columns; both directions validated by contract schemas; violations impossible by construction rather than by convention.

## 5. Status models

- Integration status (both sides): `not_connected, provisioning, connected, sync_pending, sync_warning, sync_failed, authorization_required, disconnected` (HOB list verbatim).
- Denver-derived stage shown in Nova: Denver `current_phase` + turnover chain mapped to the HOB display stages (`Planning … Client acceptance, Closed`); mapping table lives in the contract doc so both repos agree.

## 6. Consequences

**Positive:** no new infrastructure; both repos extend their own proven patterns; tenant safety by construction (connection registry + signature, RLS on all new Denver tables); honest partial-data rendering; contracts tested in both repos.

**Negative / accepted debt:**
- Two secret pairs to manage per environment (documented rotation; no in-DB secret storage in v1).
- No SSO in v1 — users need accounts in both products; deep links land on login when unauthenticated.
- Nova `fly.toml` scale-to-zero adds cold-start latency to webhook delivery (mitigated by outbox retry; recommend `min_machines_running=1` when integration goes live).
- Contract schemas are duplicated copies (checksum-tested), not a shared package.
- Denver discipline-split percents may be sparse until EVM/KPI adoption; UI shows "not reported" rather than fake zeros.

**Follow-on slices (not in scope):** OIDC/account linking; multi-connection self-service provisioning UI; turnover evidence controlled archival; Nova CI pipeline (recommended independently — Nova currently runs no tests in CI); moving Denver webhook retry to durable re-enqueue for the generic hub.
