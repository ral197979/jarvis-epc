## Health Check

```yaml
healthCheckPath: /api/v1/health
```

**Implementation** (from server.ts):
```typescript
app.get('/api/v1/health', (_req, res) => {
  res.json({ status: 'ok', version: process.env['npm_package_version'] })
})
```

**Assessment:** Health check exists but is shallow — it confirms the process is alive, not that DB or Redis are reachable. A healthy response while the DB is down is misleading.

**Recommendation:** Add DB ping to health check:
```typescript
// app.get('/api/v1/health')
const dbOk = await pool.query('SELECT 1').then(() => true).catch(() => false)
res.json({ status: dbOk ? 'ok' : 'degraded', db: dbOk })
```

## Monitoring & Observability

**What exists:**
- **Pino structured logging** — JSON logs to stdout (Render captures these)
- **Correlation IDs** — `X-Correlation-ID` header on every request ✅
- **Audit logging** — every mutation logged to `audit_log` table

**What is missing:**
- No APM (Application Performance Monitoring) — no Datadog, New Relic, or Sentry
- No error tracking (Sentry / Bugsnag) — unhandled exceptions go to Render logs only
- No distributed tracing
- No alerting on error rate spikes or latency thresholds
- No custom dashboards or metrics
- No uptime monitoring (external ping)

**Assessment:** Logging is good (Pino + correlation IDs). Alerting is absent. You will learn about production outages from users, not from monitoring.

## Database Backups

**Render PostgreSQL `standard-4gb` plan includes:**
- Daily automated backups (7-day retention on standard plan)
- Point-in-time recovery (PITR) — available on higher plans

**What is NOT configured:**
- No pg_dump backup verification (backup restore tests)
- No off-platform backup copy (backup is Render-only)
- No backup monitoring or alert on backup failure

**Risk:** Single-cloud, single-region. A Render platform incident affecting the backup could mean data loss.

## Migration Strategy on Deploy

```typescript
// api/db/migrate.ts — runs on startup
// Reads all migration files, checks schema_migrations table,
// runs new migrations in order
```

**Risk:** Migration runs on startup during deploy. If a migration fails (e.g., syntax error, constraint violation), the new container exits, Render rolls back to the previous instance. This is acceptable behavior but:
- Long-running migrations (e.g., adding index to millions of rows) will delay startup
- No `--dry-run` mode to preview changes
- No DOWN migrations to rollback a bad change
